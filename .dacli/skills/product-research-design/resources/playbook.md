# Product research and design playbook

Label inputs as observation, inference, or hypothesis. Ask for the last concrete
incident, not whether someone would like a proposed feature. Preserve source
and segment, synthesize across independent evidence, and call a need confirmed
only at the project's stated corroboration threshold.

Rank opportunities by user value, frequency, strategic fit, implementation
cost, operational risk, and reversibility. State what existing data or system
seam the proposal reuses and what new collection it requires. Every proposal
needs a falsifiable success signal and explicit non-goals.

Design specifications must name data, permissions, states, accessibility,
responsive behavior, failure/recovery, analytics where justified, and the
boundary between local CLI and optional hosted control plane.
